**Report path:** `docs/RAZORPAY_LEGACY_SECURITY_AUDIT.md`

**Date:** 2026-10-18
**Repository state audited:** working tree at commit `8bdae43` plus pre-existing uncommitted payment-workflow changes (preserved untouched; see §11.4)

## 1. Executive Summary

Razorpay is **genuinely unused by business logic**. No frontend, mobile-app, test, webhook, scheduled-job, or shared-payment-code caller invokes it. The web and React Native clients contain **zero** references to Razorpay, `rzp_`, `create-order`, or `verify-payment` (workspace-wide grep, 0 matches).

However, the legacy integration is **not fully dormant at the HTTP layer**. Two Razorpay booking routes remain registered behind authentication only, with no authorization or transaction binding:

| Route | Status |
|---|---|
| `POST /api/bookings/create-order` | **Registered, reachable** by any logged-in user. Fails with HTTP 500 *before persisting anything* when Razorpay keys are absent (the current observed configuration). If keys are ever configured, it creates real Razorpay orders and `pending_payment` bookings. |
| `POST /api/bookings/verify-payment` | **Registered, reachable** by any logged-in user. Confirmed weaknesses (dynamically reproduced, §6): no ownership check, no booking↔signature binding, no idempotency, no payment-provider check. Fails closed only *incidentally* when keys are absent. |
| `POST /api/marketplace/orders/verify` | Registered but **explicitly disabled — HTTP 410**, no state mutation. Correct. |

The `verifyPayment` handler was **dynamically validated in an isolated local environment**: a valid Razorpay signature for a completely unrelated order marked **another user's PhonePe booking** as `paid / FULLY_PAID` (scenario S2), and the same signature replayed against a different booking succeeded as well (S3). Signature verification correctly runs **before** any mutation and invalid signatures cause no state change (S1).

**Exploitability is constrained but real**: forging or replaying a signature requires (a) Razorpay credentials configured on the server (currently absent from all configuration surfaces observed in this repository, and the local `.env` contains no `RAZORPAY_*` variables), and (b) a source of one valid signature — legacy signatures are stored in booking records and returned by booking APIs (§4, RZP-07), or one can be obtained through the reachable `create-order` path plus Razorpay's hosted checkout if keys are configured.

**Decision (Phase 7): C — LEGACY_SECURITY_RISK.** The path is reachable and has confirmed, dynamically demonstrated payment-state corruption weaknesses. In the currently observed configuration the practical impact is dormant (fail-closed), so severity is recorded as *High, conditional on credential configuration* rather than Critical.

**No active payment flow depends on Razorpay code.** PhonePe, mock-payment, and booking workflows import nothing from `src/utils/razorpay.js`; existing payment suites pass unchanged (§11).

## 5. Findings

Severity scale: Critical / High / Medium / Low / Informational. Confidence: how strongly the evidence supports the finding. Status: Open (unless noted).

### RZP-01 — Missing authorization and transaction binding on `verifyPayment` (IDOR → arbitrary booking marked paid)
- **Severity:** High *(conditional — see §8 prerequisites)*
- **Confidence:** High (dynamically reproduced)
- **Status:** Open
- **Evidence:** `booking.routes.js:14`; `booking.controller.js:199-227` — `bookingId` and all Razorpay fields come from the request body (:201); signature is validated only over `orderId|paymentId` (`utils/razorpay.js:28-35`); the booking's `razorpayOrderId` (:183) is **never compared** to the submitted one; `userId` is never checked; `findByIdAndUpdate` runs directly (:206-213).
- **Dynamic proof:** Scenarios **S2** and **S3** (§6): a valid signature for an unrelated order marked *another user's PhonePe booking* `paid/FULLY_PAID` (HTTP 200), and the same signature worked again against a different booking.
- **What the signature does and does not prove:** It proves *some* Razorpay payment of *some* amount occurred for *some* order — it does **not** prove this user owns this booking, that this payment was for this booking, or that the amount matches. Signature validity is therefore not a substitute for the missing association checks.

### RZP-02 — Cross-provider and arbitrary-status state interference
- **Severity:** Medium
- **Confidence:** High (dynamic S2 + static)
- **Status:** Open
- **Evidence:** No `paymentProvider` check (`Booking.js:66` field ignored by the handler) and no current-`status` guard (`Booking.js:78-84` enum — handler writes `'paid'` unconditionally at :209). Dynamic S2 flipped a `paymentProvider:'phonepe'` booking with a Razorpay signature.
- **Consequences:** (i) A PhonePe booking can be marked paid without PhonePe money — `verifyPhonePePayment` then early-returns `alreadyVerified` (booking.controller.js), so the genuine PhonePe flow is preempted; (ii) the mock control plane's eligibility check (booking must be `pending_payment`) starts returning 409; (iii) bookings in `completed`/`refunded`/`cancelled` states can be rewritten to `paid`.

### RZP-03 — Non-idempotent verification with duplicate side effects
- **Severity:** Medium
- **Confidence:** High (dynamic S4)
- **Status:** Open
- **Evidence:** No already-paid guard in `verifyPayment`. Dynamic S4: two re-verifications of an already-paid booking returned HTTP 200 and `Pooja.totalBookings` incremented **2→4**. Each call re-runs :216-220 (`save()`), :222 (`$inc totalBookings`), :223 (`PAYMENT_SUCCESS` + `BOOKING_CONFIRMED` emissions) and `fireReferralNotifications` (`booking.controller.js:103-125` — re-appends `BOOKED`/`PENDING_REMARK` to `referral.statusHistory` and re-emits two referral notifications).
- **Impact:** Duplicate customer-facing notifications, inflated booking counters, duplicated referral state history; no double money movement (there is none in this path at all).

### RZP-04 — Signature verification secret has no presence/emptiness guard
- **Severity:** Medium *(conditional on misconfiguration)*
- **Confidence:** High (dynamic S5, S6; static)
- **Status:** Open
- **Evidence:** `utils/razorpay.js:31` reads `process.env.RAZORPAY_KEY_SECRET` directly inside `verifySignature` — unlike `getRazorpay()` (:8-9), there is no explicit guard.
  - **Secret absent** → Node throws `ERR_INVALID_ARG_TYPE` from `createHmac` → handler's `catch` → HTTP 500, **no mutation** (dynamic S5). Fail-closed behavior is *incidental* (a TypeError), not an intentional check.
  - **Secret set to empty string** → HMAC over an empty key is computable by anyone → forged signature accepted → booking marked paid (dynamic S6, HTTP 200 confirmed).
- **Note:** An empty `RAZORPAY_KEY_SECRET=` in an environment file would silently disable all signature protection.

### RZP-05 — Timing-unsafe signature comparison
- **Severity:** Low
- **Confidence:** High (static)
- **Status:** Open
- **Evidence:** `utils/razorpay.js:34` — `expected === signature` (early-exiting string compare, not `crypto.timingSafeEqual`).
- **Practical note:** Network jitter makes exploitation difficult, but the fix is trivial (fixed-length hex + `timingSafeEqual`).

### RZP-06 — Verification writes no PaymentLedger / payment-attempt record
- **Severity:** Low
- **Confidence:** High (static)
- **Status:** Open
- **Evidence:** `verifyPayment` mutates only `Booking`, `Pooja`, `Referral` and emits notifications — `PaymentLedger` (`paymentStatus: PENDING|SUCCESS|FAILED`, `PaymentLedger.js:7`) and `paymentAttempts` are never touched, unlike the PhonePe flows.
- **Impact:** After a Razorpay verification, the booking reads `FULLY_PAID` while its ledger rows (if any) remain `PENDING` — reconciliation and admin views can disagree; no automated cross-check exists.

### RZP-07 — Non-expiring signature material stored and returned by booking APIs
- **Severity:** Low (enabler for RZP-01 when keys are configured)
- **Confidence:** High (static)
- **Status:** Open
- **Evidence:** `Booking.js:70` stores `razorpaySignature` with no `select:false`; `getMyBookings` (booking.controller.js:835-854) returns full documents to the owner; `getBookingById` (:866-897) returns full documents to owner/admin/assigned pandit (authorization exists at :877-892, but no field exclusion); `admin.controller.js` contains **zero** razorpay-field exclusions (0 grep matches). Only the pandit **list** projection excludes them (`pandit.controller.js:31`).
- **Impact:** Razorpay signatures never expire. Any readable legacy signature is permanent replay material for RZP-01 on any server where the secret is configured.

### RZP-08 — Reachable legacy order-creation path
- **Severity:** Low
- **Confidence:** High (dynamic S8 + static)
- **Status:** Open
- **Evidence:** Route matrix #1. With keys absent: `getRazorpay()` throws before `Booking.create` — dynamic S8 observed `nextErr="Razorpay keys are not configured"` and **0 bookings persisted**. With keys configured: any authenticated user can create real Razorpay orders and `pending_payment` bookings through an officially deprecated flow (client-side checkout is never initiated by any frontend/mobile code).
- **Impact:** Dorman abuse/ops surface (gateway-order creation, orphaned pending bookings); no direct fraud by itself.

### RZP-09 — Error-message state disclosure
- **Severity:** Informational
- **Confidence:** High (static)
- **Status:** Open
- **Evidence:** Global error handler returns `err.message` with status 500 (`app.js:200-207`). The thrown message `Razorpay keys are not configured (RAZORPAY_KEY_ID / RAZORPAY_KEY_SECRET)` (`utils/razorpay.js:9`) tells any caller whether Razorpay credentials are absent — useful reconnaissance for judging RZP-01 exploitability.

### RZP-10 — Positive control: marketplace `verifyOrder` correctly disabled
- **Severity:** Informational (control, not a defect)
- **Status:** N/A — working as intended
- **Evidence:** `marketplace.controller.js:498-500` returns 410 before any logic; confirmed by router stack (`protect > handler`).

## 8. Business Impact and Exploitability Prerequisites

### What an attacker could achieve (RZP-01)
Mark **any booking in the database** — other users' bookings, PhonePe bookings, bookings in any status — as `paid / FULLY_PAID`, triggering confirmation notifications and referral progression, **without paying the amount that booking requires**.

### Prerequisites (all must hold)
1. **Server has `RAZORPAY_KEY_SECRET` configured.** Not observed in this repository (`.env` has no `RAZORPAY_*`; `.env.production.example` contains none; `DEPLOYMENT_CONFIGURATION.md:116` marks the keys *"No (legacy)"*). Production deployment state **cannot be verified from the repository** (§12). When absent, the handler fails closed (S5) — impact is dormant.
2. **A source of one valid signature**, obtainable by:
   - **Legacy signatures already in the database** (old Razorpay bookings) — readable by the booking's owner through `getMyBookings`/`getBookingById`, by admins, and by assigned pandits via `getBookingById` (RZP-07). Signatures never expire; **or**
   - **Creating a real payment**: call the reachable `POST /api/bookings/create-order` (works when keys are configured) to obtain a genuine order id, then complete payment through Razorpay's hosted checkout using the public `key_id` — in Razorpay **test mode** this needs no real money.
3. **An authenticated account** (self-registration availability not assessed) and passing rate limits.

### What is NOT possible
- No unauthenticated exploitation (401 without JWT).
- No exploitation when keys are absent (current observed state) — verified, not assumed (S5, S8).
- No secret extraction: no hardcoded key material exists anywhere searched (§7).
- No double money movement: this path never charges anyone — the fraud mode is *state falsification*, not duplicate charging.
- No direct interference with PhonePe/mock code paths by import: active providers never load the Razorpay utility (§3.1); interference occurs only at the **data level** via RZP-02.

### Severity rationale (why not Critical)
The handler is behind authentication, rate-limited, and — in the observed configuration — fail-closed. The missing checks are nonetheless confirmed and dynamically demonstrated, and one read-only legacy signature escalates to full payment-state forgery wherever the secret is present. Hence **High (conditional)**.

## 9. Recommended Remediation (for approval — NOT implemented)

**Priority 1 — neutralize reachability (smallest, safest change):**
1. Disable `POST /api/bookings/verify-payment` exactly like `verifyOrder`: return **410** with `"Razorpay payments are no longer supported. Use PhonePe."` (`booking.controller.js:199`), and likewise disable `POST /api/bookings/create-order` (`:148`) — no frontend/mobile caller exists, so no user impact. Keep the route *registered-but-410* if path-availability monitoring matters, or remove both routes outright.

**Priority 2 — if the owner ever chooses to retain the flow, fix in this order:**
2. Ownership: `booking.userId` must equal `req.user._id` before any read/write.
3. Binding: require `booking.razorpayOrderId === razorpayOrderId`, `booking.paymentProvider === 'razorpay'`, `booking.status === 'pending_payment'`; ideally verify captured amount against the booking via the gateway API (server-side) rather than trusting the client tuple alone.
4. Idempotency: early-return `alreadyVerified` when already `FULLY_PAID` (mirroring `verifyPhonePePayment`).
5. Secret hygiene: explicit `if (!secret) throw` guard in `verifySignature` (fail 503), reject empty strings.
6. Constant-time comparison: hex-normalize both sides, `crypto.timingSafeEqual`.
7. Write `PaymentLedger`/payment-attempt records for reconciliation (RZP-06).
8. Set `razorpaySignature: { select: false }` (or stop storing signatures) and exclude it from all booking API responses (RZP-07).

**Priority 3 — removal (separate, explicitly approved change):**
9. After confirming no operational need to re-verify historic bookings: delete the two routes + handlers, `utils/razorpay.js`, the `razorpay` dependency from `package.json`, and the `.env.example` entries. **Keep** the `Booking`/`Order` schema fields (read-only legacy data) unless a data migration is approved. Keep `healthReport.js` entry only if keys remain set anywhere.

## 13. Final Decision

# C — LEGACY_SECURITY_RISK

**Selected outcome:** **C. LEGACY_SECURITY_RISK** — reachable paths with confirmed, materially concerning security weaknesses.

**Evidence supporting the selection:**
1. **Reachability is proven, not assumed:** `POST /api/bookings/verify-payment` and `POST /api/bookings/create-order` are registered (`app.js:158`), mounted behind authentication only (`booking.routes.js:11`), confirmed by router-stack introspection, and their handlers execute real logic (dynamic S1–S8 exercised the actual controller code).
2. **Weaknesses are confirmed and dynamically reproduced:** arbitrary-user booking marking (S2), cross-booking signature replay (S3), cross-provider status flip (S2), non-idempotent double-processing (S4), empty-secret forgery (S6). These are code defects independent of deployment configuration.
3. **Mitigating factor recorded, not ignored:** under the currently observed configuration (no Razorpay credentials anywhere in the repository), the handler fails closed (S5) and order creation persists nothing (S8) — so real-world impact today is dormant. This constrains exploitability but does not remove the finding; a single future `RAZORPAY_KEY_SECRET=` entry (even empty) reactivates it.
4. **Option B is subsumed:** the integration is indeed *unused but reachable* — C is selected because the reachable path additionally carries confirmed security weaknesses, taking precedence per the classification rules. Options A and D are excluded by evidence: routes are reachable (not A), and no active provider imports Razorpay code (not D — only schema fields and a notification-text fallback are shared). E is excluded: repository evidence was sufficient for every material claim in this report.

**Remediation direction (approval-gated):** disable both booking routes with 410 parity now (§9 Priority 1), then remove the integration in a separately approved change (§9 Priority 3). No credential rotation is warranted — no secret exposure was found. **No fixes were implemented in this audit.**
